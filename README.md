# 基于 STM32 + 树莓派的智能小车

一个四端协同的智能小车系统：**STM32** 负责实时运动控制，**树莓派**负责网络服务与多媒体，**手机端**提供 Qt 图形界面，另有自绘 PCB 承载硬件连接。

支持 **避障 / 红外循迹 / 手动遥控** 三种运动模式，以及音乐播放、语音交互、实时视频、录像拍照、传感器数据显示和 PID 在线调参。

**技术栈**：C（HAL）· Python · C++ / Qt · Linux · UART / TCP · 自定义二进制协议 · MJPEG

## 二、系统架构
a
```
   ┌──────────────┐   UART     ┌────────────────────┐  WiFi/TCP   ┌──────────────┐
   │    STM32     │◄──────────►│     树莓派 5B       │◄───────────►│ Qt Android   │
   │  实时控制     │  自定义     │      多线程       │  自定义协议  │   手机端      │
   │              │  二进制帧   │                    │             │              │
   └──────┬───────┘            └─────┬────────┬─────┘             └──────────────┘
          │                          │        │
   ┌──────┴───────┐           ┌──────┴──┐  ┌──┴─────────┐
   │ 电机 / 舵机   │           │  CSI    │  │ 麦克风      │
   │ 陀螺仪        │           │ 摄像头   │  │ 扬声器      │
   │ 超声波/红外   │           └─────────┘  └────────────┘
   └──────────────┘
```

**数据流**

1. STM32 采集传感器并执行运动控制 → 串口发送二进制帧给树莓派
2. 树莓派解析后转为 JSON → 经 WiFi/TCP 推送到手机显示
3. 手机下发的控制命令与 PID 参数 → 树莓派透传给 STM32
4. 视频链路独立：树莓派采集编码 → 8889 端口 → 手机解码显示

**端口划分**

| 端口 | 用途 |
|---|---|
| 8888 | 命令 + 传感器数据 |
| 8889 | 视频流 |

拆成两个端口是为了**避免大流量视频阻塞控制通道**——视频混在命令连接里会把控制指令挤在后面，直接恶化操作手感。

## 三、三端职责

### STM32 端（C / CubeMX + HAL）

- 三种运动模式：手动遥控、超声波避障、红外循迹，可通过串口指令切换
- **串级双闭环 PID** 直行控制（编码器内环 + 陀螺仪外环）
- 定时器编码器模式采集电机脉冲
- 定时器输入捕获 + 中值滤波读取超声波测距
- 五路红外加权计算偏移量，P 控制循迹
- ADC + 降压电路读取电池电压，估算剩余电量
- 手动模式带指令超时保护：一段时间未收到指令自动停车

### 树莓派端（Python / 9 类线程）

| 线程 | 职责 |
|---|---|
| 串口读取 | 解析 STM32 的二进制帧与调试文本帧 |
| 命令处理 | 消费命令队列，单写者执行音乐 / 语音 / 客户端命令 |
| 主服务器 | 监听 8888，为每个客户端创建处理线程 |
| 客户端 | 收发命令与传感器数据（每连接一个实例） |
| 摄像头服务器 | 采集 → JPEG 编码 → 8889 推流 |
| 音乐状态 | 周期性上报播放进度、歌曲索引、播放状态 |
| 音频采集 | 按订阅者开关麦克风，避免无效采集 |
| 唤醒词 | Vosk 离线识别 + 拼音相似度匹配 |
| 语音识别 | 百度 ASR + 拼音匹配触发命令 |

### 手机端（C++ / Qt Android）

- `QStackedWidget` 多页面：控制 / 传感器 / 音乐 / 参数调试 / 实时画面 / 语音交互 / 轨迹
- 手动控制按钮（长按持续运动）、三种模式切换
- 传感器数据实时显示，PID 参数在线下发（带输入类型校验）
- 视频解码显示与镜像处理，支持录像与拍照、本地存储
- 录像通过自实现的 MP4 封装写入，**用采集时间戳构建 STTS 表**以还原真实时间轴

## 四、通信协议

除 PID 调试文本外，所有数据包统一采用：

```
┌──────────┬───────────┬───────────┬────────┐
│   帧头    │  帧体长度  │    帧体    │  CRC8  │
│ 0xAA 0x55│  1 byte   │  N bytes  │ 1 byte │
└──────────┴───────────┴───────────┴────────┘
```

统一格式的好处是**半包 / 粘包处理逻辑可以复用**，不需要为每类数据写一套解析。

**帧体内容按类型区分**

| 方向 | 类型 | 帧体内容 |
|---|---|---|
| STM32 → 树莓派 | 传感器数据 | 命令 + 温湿度 + 左右编码器 + 电池 ADC + 偏航角 |
| 树莓派 → STM32 | 控制命令 | 命令 + 参数（变长） |
| 树莓派 → 手机 | 传感器 JSON | JSON 文本 |
| 树莓派 → 手机 | 视频流 | 时间戳 + JPEG 字节流 |
| 手机 → 树莓派 | 控制命令 | 命令 + 参数（变长） |

**PID 调试文本包**：`$` + 调试文本 + `*\r\n`（与二进制包共存，解析时按帧头位置判断先后）

**半包 / 粘包处理流程**

```
数据写入缓存区
  ├─ 查找帧头 0xAA55
  │    未找到 → 仅保留最后 1 字节（可能是帧头前半），break
  │    找到   → 丢弃帧头之前的垃圾数据
  ├─ 缓存区 < 帧头 + 长度字段  → break（半包，等待下次数据）
  ├─ 解析帧体长度
  │    非法（0 或过大）→ 丢弃 1 字节，重新查找帧头
  ├─ 缓存区 < 完整包长度      → break（半包）
  ├─ CRC8 校验（覆盖长度字段 + 帧体）
  │    失败 → 丢弃 1 字节，重新查找帧头
  └─ 校验通过 → 处理帧体
```

## 五、关键技术点

### 1. STM32：串级双闭环 PID

**控制结构**：外环（陀螺仪航向）→ 输出两轮差速 → 内环（编码器速度差）→ PWM

**为什么用双环**：内环只能保证两轮转速一致，但车整体仍会偏航，需要航向闭环来解决。代价是调试量变大。

**为什么每个环节都只用 P**

| 环节 | 结论 | 依据 |
|---|---|---|
| 内环 I | 不用 | 给定 Kp 跑 5 米，左右轮总脉冲数几乎一致 → 偏移源于机械结构与打滑，I 起不到作用，反而放大噪声 |
| 内环 D | 不用 | 编码器 20ms 采样，分辨率低、量化噪声大且采样时间不固定，微分会放大噪声 |
| 外环 I/D | 不用 | MPU6050 存在零漂，静止时读数持续单向漂移，积分会累积该误差；同样噪声大，不适合微分 |

**实测调参数据**

| 环节 | 现象 | 最终取值 |
|---|---|---|
| 内环 P | 130 可直行；150 出现高频小幅抖动 | **90**（临界值的 60%） |
| 内环 I | 0→4 差异不大；5 开始小幅抖动 | **0** |
| 外环 P | 0–2.5 平稳；3 低频振荡；5 出现画龙 | **2**（临界值的 60%） |

### 2. 树莓派：单写者线程模型

把所有**会改变状态**的操作（音乐、语音会话）收敛到**命令处理线程**单线程执行：

- 语音识别线程、客户端线程产生的命令不直接执行，统一入队
- 消除写-写互斥 → 跨线程读取只需一把轻量锁保证**快照一致性**
- 单写者场景下不存在死锁可能

**锁的优化**：广播函数原本在锁内直接 `send`，由于 `send` 是耗时操作会拖慢全局，改为「**锁内只做客户端列表快照、锁外发送**」。

**边界说明**：串口**不需要加锁**——只有命令处理线程写、只有串口读取线程读，全双工互不干扰。

### 3. 视频链路

| 决策 | 选择 | 理由 |
|---|---|---|
| 编码 | MJPEG（逐帧独立 JPEG） | Qt 端解码简单、延迟低；代价是码率高于 H.264 |
| 传输 | 自定义协议 + TCP | 单客户端、自研客户端、局域网，不需要兼容标准播放器 |
| 端口 | 独立 8889 | 避免视频流量阻塞控制通道 |
| 时间戳 | 每帧携带采集时间戳 | 录制时用于构建 MP4 的 STTS 表，保证时长与实际一致 |

**已知代价**：TCP 存在**队头阻塞**——丢包会导致后续帧等待重传。局域网丢包率极低所以可接受；公网场景需改用 UDP + RTP。

**关于容器格式**：早期使用 AVI（固定帧率容器），由于网络传输帧率波动，录制时长与实际不符；改为 MP4 后利用其可变帧率特性，**按相邻帧时间戳差值构建 STTS 表**，时间轴得以还原。代价是 VFR 视频在部分播放器 / 剪辑软件上兼容性一般。

### 4. 异常容错（三层）

1. **线程级兜底**：`try` 置于 `while` **内部**，异常后继续下一轮循环，避免线程静默死亡
2. **异常分类处理**（以摄像头线程为例）
   - `socket.timeout`：跳过当前帧，不断开连接
   - 连接断开（`BrokenPipeError` / `ConnectionResetError`）：跳出内层循环回到 `accept`
   - 其他异常：记录日志后同样回到 `accept`
   - `finally` 保证清理：清除事件标志、释放 8889 端口、释放摄像头硬件
3. **状态机兜底**：语音会话具备**幂等守卫**（`enter` / `exit` 重复调用直接返回）与**超时强制复位**（超过 30 秒强制退出）

### 5. 常驻线程与功耗

摄像头、音频采集、唤醒词、语音识别均为**常驻线程**，用标志位控制是否工作——省去每次开启的初始化加载时间。

**但线程常驻 ≠ 硬件常开**：真正耗资源的是采集动作本身。音频采集线程采用**订阅者机制**——唤醒词与语音识别线程开始工作时订阅、停止时取消订阅，**无订阅者时关闭麦克风**。

## 八、已知限制

- **摄像头通道仅支持单客户端**：视频是带宽瓶颈，多客户端会导致带宽线性增长；第二个客户端会停留在 `backlog` 队列
- **采集与发送在同一线程**：发送阻塞会影响采集节奏，当前用短超时 + 丢帧缓解，多客户端场景需解耦为「采集线程 + 每客户端发送线程 + 共享帧缓冲」
- **视频传输使用 TCP**，存在队头阻塞
- **MP4 封装的 STTS 表未做游程压缩**：相同间隔的帧本可合并，长时录制会产生较大索引表
- **`stco` / `mdat` 使用 32 位偏移**：文件超过 4GB 会溢出，长时录制需改用 `co64`
- **PCB 为模块化集成**（排针 / 排母接口），非芯片级设计
